# 03. Database changes (`supabase/`)

Everything here is new unless it says "changed". The conventions of `docs/spec/03-database.md` apply unchanged: snake_case, `uuid` keys from `gen_random_uuid()`, `timestamptz` instants, integer paise, RLS enabled in the migration that creates a table, `set search_path = public, extensions` on every function, a header comment with the contract and error codes, and `revoke execute on function … from public, anon, authenticated` immediately after each `create function`, followed by the grant stated here (`service_role` keeps its default grant). Two rules are added:

- A migration that creates a table or a view ends with `revoke insert, update, delete, truncate, references, trigger on <it> from anon, authenticated;`. Supabase's default privileges grant `ALL` on new objects in `public`, and RLS never applies to `truncate` (migration `20261104122800`). pgTAP 001 gains a schema-wide assertion, so forgetting the revoke fails CI.
- No value is added to an existing enum. A new value needs a migration of its own, because `scripts/db/local.sh` applies each file in one transaction and Postgres cannot use an enum value in the transaction that added it. The one new enum here is a new type, which a migration may create and use at once.

The Homebrew shim (`supabase/local/shim.sql`) gains one column, `auth.users.phone_confirmed_at timestamptz`, which GoTrue's own table has. The new SQL reads `auth.users.id`, `phone` and `phone_confirmed_at`, and the access token's `amr` claim through `auth.jwt()`, which the shim already defines; M7 deletes a row from `auth.users`, which the shim's table allows. The Storage and pg_cron parts are guarded as in iteration 1.

## Enum

`booking_block_kind`: `walk_in, phone, other_app, maintenance, event, other`. The kind of a counter block: a walk-in seated at the desk, a phone or WhatsApp booking, a booking taken on another app, a station under maintenance, a private event, anything else.

## Changed tables

### `bookings` select policy (M0)

Migration `20261117120000`, before any membership exists, replaces iteration 1's policy:

```sql
drop policy "bookings: owner or cafe member can read" on public.bookings;
create policy "bookings: the booker can read"
  on public.bookings
  for select
  to authenticated
  using (user_id = (select auth.uid()));
```

The member branch let any member read every booking of their cafe through PostgREST with their own session, and `bookings` and `booking_details` (which selects `b.*`) both carry `user_id`, which links one player's visits over time and across cafes (ADR 0017). Nothing needs it: `listMine` reads `my_booking_details` (M0), `cancel_booking` loses its member branch (M1), and cafes read bookings only through the partner functions. `booking_seats` follows through its parent subquery, unchanged.

## New tables

All have RLS enabled with no policy, so `anon` and `authenticated` read zero rows, and table writes are revoked. Only the functions below read and write them.

### `platform_operators` (M1, ADR 0014)

`phone text primary key check (phone ~ '^[1-9][0-9]{6,14}$')` (GoTrue's digits-only form, as `auth.users.phone` and `profiles.phone` hold it), `created_at timestamptz not null default now()`. No migration, seed or other committed file inserts a row.

### `cafe_invites` (M1)

`id`, `cafe_id → cafes (cascade)`, `phone text not null check (phone ~ '^91[6-9][0-9]{9}$')`, `role cafe_member_role not null`, `invited_by → auth.users (set null)`, `created_at`, `expires_at timestamptz not null default now() + interval '14 days'`, `accepted_at timestamptz`, `accepted_by → auth.users (set null)`, `revoked_at timestamptz`, `revoked_by → auth.users (set null)`, `check (accepted_at is null or revoked_at is null)`. An index predicate cannot call `now()`, so an expired invite keeps its slot in the unique index until `invite_cafe_member` revokes it (below).

### `partner_terms_acceptances` (M1)

## Views

### `my_booking_details` (M0; changed in M5)

`with (security_invoker = true)`. M0: `select d.* from public.booking_details d where d.user_id = (select auth.uid())`. M5 replaces it with `create or replace view public.my_booking_details with (security_invoker = true) as select d.*, b.cancel_reason as cafe_cancel_reason from public.booking_details d join public.bookings b on b.id = d.id where d.user_id = (select auth.uid())`; the new column comes last, which `create or replace view` allows. The `with` clause must be repeated: `create or replace view` replaces the view's options with the new statement's, even when it states none (`src/backend/commands/view.c`, `DefineVirtualRelation`, REL_17_STABLE, read 16 Nov 2026), and without it the view would read `bookings` as its owner. `listMine` reads this view instead of `booking_details`, so "My bookings" is filtered by the view as well as by the booker-only bookings policy. Writes revoked; `select` stays granted (RLS and the filter apply).

### `partner_booking_details` (M1)

`with (security_invoker = true)`. The shape every partner booking function returns (ADR 0017): `id, cafe_id, cafe_name, tier_id, tier_name, tier_kind, source, block_kind, note, status, starts_at, ends_at, seat_count, hourly_rate_paise, total_paise, hold_expires_at, created_at, acknowledged_at, checked_in_at, closed_at, cancel_reason, no_show_grace_minutes` (the booking's copy), and `seats jsonb` = `coalesce((select jsonb_agg(jsonb_build_object('station_id', bs.station_id, 'station_label', bs.station_label, 'starts_at', lower(bs.during), 'ends_at', upper(bs.during), 'released_at', bs.released_at) order by bs.station_label, lower(bs.during)) from booking_seats bs where bs.booking_id = b.id), '[]'::jsonb)`. It has no `user_id`, no actor ids and nothing from `profiles`.

Clients do not read it directly: `revoke select … from anon, authenticated` together with the write revoke, so the partner functions are the only read path. A function's return type does not need `select` on the view; verify on the local stack that PostgREST serves a function returning this row type to `authenticated` after the revoke. If it does not, keep `select` granted: the booker-only bookings policy then limits direct reads to the caller's own bookings.

## Error codes

Iteration 1's `GG001`–`GG009` keep their meanings. New codes start at `GG010`, the next free one:

| SQLSTATE | Meaning                                                                                                                          | `PartnerErrorCode` |
| -------- | -------------------------------------------------------------------------------------------------------------------------------- | ------------------ |
| `GG010`  | Forbidden: the caller has a role at the cafe, but not one this action allows; or a non-operator called an operator-only function | `forbidden`        |
| `GG011`  | Invalid input to a partner function; the message names the field                                                                 | `invalid_input`    |
| `GG012`  | Conflict with existing data: a duplicate, bookings the change would break, or references that prevent a delete                   | `conflict`         |
| `GG013`  | The change would leave the cafe without an owner                                                                                 | `last_owner`       |
| `GG014`  | The cafe is not ready to be published, to take app bookings or to be approved for them; the message lists what is missing        | `not_ready`        |

Partner functions also raise `GG001` (`auth_required`), `GG004` (`not_enough_seats`), `GG005` (`seat_conflict`, retried once by the data layer), `GG007` (`not_found`) and `GG008` (`invalid_state`). The booking functions' new rules reuse `GG002`, `GG003` and `GG006` (below), so `BookingErrorCode` does not change. Messages are short English for developers; clients map codes, never messages.

## Functions

All `language plpgsql` unless noted, `security definer` unless noted, granted to `authenticated` only unless noted. "Owner, staff, operator" means the function calls `require_cafe_role` with those roles (`02-roles-and-permissions.md`): no signed-in user is `GG001`, no role at the cafe is `GG007`, a role not in the list is `GG010`. A function that takes the id of something belonging to a cafe (a booking, tier, station, invite, closure or image) first finds that row, raising `GG007` when there is none, and then checks the caller's role at its cafe, so a stranger cannot tell a missing row from someone else's; a booking is found with `select … for update`, so concurrent transitions queue as in iteration 1. Functions that allocate or move seats take the per-tier advisory lock of `create_booking`, `pg_advisory_xact_lock(hashtext('station_tier'), hashtext(<tier id>::text))`, and catch `exclusion_violation` as `GG005`. Functions that refuse a change because it would break an app booking (`set_station_active`, `set_cafe_hours`, `add_cafe_closure`) take the same lock before their check: one tier's, or every tier of the cafe in tier-id order, so a booking committed at the same moment cannot slip past the check (ADR 0016). Parameters that callers may leave empty are declared `default null` and come after the required ones, because postgres-meta types only parameters with a default as optional and the generated `Args` never accept `null` (`packages/data/src/database.types.ts`). "Audited `x`" means the function calls `partner_audit(cafe, role, 'x', subject, details)` after its change.

### Access helpers (M1)

- `has_phone_number(p_text text) returns boolean`: `language sql immutable`, invoker, granted to nobody. `regexp_replace(coalesce(p_text, ''), '[\s().+-]', '', 'g') ~ '[0-9]{7,}'`: a run of seven or more digits once spaces, dots, brackets, plus signs and hyphens are removed. Used by the check constraints above and by the functions before they write, so callers get `GG011` rather than `23514`. pgTAP 007: `'Rahul 98765 43210'` and `'+91-98765-43210'` are true; `'Booked 2 PCs 7-9 pm'` and `'Squad of 5, back at 11:30'` are false.
- `is_otp_session() returns boolean`: `language sql stable`, invoker, granted to nobody. `select coalesce(auth.jwt() -> 'amr', '[]'::jsonb) @> '[{"method": "otp"}]'::jsonb`: true when the caller's access token says its session was opened with an SMS code. GoTrue records the sign-in method on the session (`otp` for a verified phone code, `password` for a password grant) and repeats the session's methods in every refreshed token, as `amr: [{"method": "otp", "timestamp": …}]` (`supabase/auth` master, `internal/api/verify.go`, `internal/models/factor.go` and `sessions.go`, read 16 Nov 2026). Every partner role check goes through it (ADR 0014): GoTrue lets someone who does not hold a SIM register its number with a password before the holder's first sign-in, and the holder's later code sign-in confirms that account without clearing the password (`internal/api/signup.go`, `verify.go`, `internal/models/user.go`). A password on the account proves nothing, because every code sign-up also stores a random 64-character temporary password (`internal/api/otp.go`), so the check is on how the session was opened. pgTAP 007: true for `[{"method":"otp","timestamp":0}]`; false for `password`, for claims without `amr` and without claims. The M1 contract cases prove the claim's shape on GoTrue itself: if it differs, the personas see no cafes and the suite fails.
- `is_platform_operator() returns boolean`: `language sql stable`, definer, granted to `authenticated`. `select public.is_otp_session() and exists (select 1 from public.platform_operators o join auth.users u on u.phone = o.phone where u.id = (select auth.uid()) and u.phone_confirmed_at is not null)`. False without a session, for a session opened any other way than an SMS code, and for an account whose phone is unconfirmed. It answers only for the caller. Verify on the CLI stack that the definer can read `auth.users.phone_confirmed_at`. pgTAP 007: false without `sub`; false for a member; true once the caller's phone is inserted; false for the same user when the claims' `amr` is `password`; false for a user with that phone and `phone_confirmed_at` null; false again in the same transaction after the row is deleted.
- `cafe_role(p_cafe_id uuid) returns text`: `stable`, definer, granted to nobody. `'operator'` when `is_platform_operator()` and the cafe exists; otherwise, when `is_otp_session()`, the caller's `cafe_members.role::text` for the cafe; otherwise `null`. So a session opened with a password has no role at any cafe, and gets `GG007` from every partner function, although it shares the member's user id.
- `require_cafe_role(p_cafe_id uuid, p_allowed text[]) returns text`: `stable`, invoker, granted to nobody. Raises `GG001`, then `GG007` when `cafe_role` is null, then `GG010` when the role is not in `p_allowed`; returns the role.
- `partner_audit(p_cafe_id uuid, p_actor_role text, p_action text, p_subject_id uuid, p_details jsonb) returns void`: invoker, granted to nobody; one insert into `partner_audit_log` with `actor_id = auth.uid()`.

### Changed booking functions

**`cancel_booking(p_booking_id uuid)`** (M1). Same signature, return type and grants. The member branch is removed: `GG007` when `v_booking.user_id is distinct from v_user_id`, never `<>`, which is null for a counter block, so plpgsql's `if` would skip the raise and let any caller who holds a block's id cancel it past `cafe_cancel_booking` and its audit row. `GG008` when the status is not `held` or `confirmed`, and also when `checked_in_at` is not null or `now() >= starts_at`: from its start a booking is resolved at the counter (check-in, no-show or the cafe's cancellation), so a squad cannot free a seat it is sitting at, nor turn a no-show into a cancellation. It also sets `closed_at` and `closed_by`. pgTAP 004 changes its member case: a member of the cafe now gets `GG007`; the booker still cancels before the start; the booker gets `GG008` once the start has passed and for a checked-in booking (the test moves the row's times and sets `checked_in_at` directly); a counter row inserted directly (`source 'counter'`, no user) gets `GG007` from a stranger and from the cafe's own staff and stays confirmed with its seats unreleased.

**`confirm_booking(p_booking_id uuid)`** (M1, in the same migration). Re-created with `if not found or v_booking.user_id is distinct from v_user_id then` and nothing else changed, so a counter block answers `GG007` rather than `GG008`, and a hold whose `user_id` account deletion has nulled (M7) cannot be confirmed by anyone who holds its id. pgTAP 004: the directly inserted counter row gets `GG007` from `confirm_booking` too.

**`create_booking(…)`** (M2). Same signature, return type and grants. The steps of `docs/spec/03-database.md` change as follows:

- Step 3 also raises `GG006` ("cafe is not taking app bookings") when `app_bookings_enabled` is false.
- New step 3b: `GG002` ("start must be at least N minutes from now") when `p_starts_at < now() + app_notice_minutes`. The global five-minute floor of step 2 stays.
- New step 4b: `GG003` ("the cafe is closed then") when a closure of the cafe overlaps `[start, end)`.
- After taking the tier lock in step 6, steps 4 and 4b run again in a new statement, which sees any hours or closure committed while the call waited for the lock; `set_cafe_hours` and `add_cafe_closure` take the same lock before their own checks, so either the booking or the change is refused.
- Step 6b allocates only stations with `is_active and is_app_bookable`.
- Step 7 copies the cafe's `no_show_grace_minutes` into the booking.
- The per-account caps of step 5 are unchanged and count app rows only (counter rows have no user).

pgTAP 010: each new rule raises its code; allocation never picks an unpledged station; a new booking carries the cafe's grace period; with every station pledged and the switch on, the iteration-1 tests pass, except that 006's case "every station is free when there are no bookings" (lines 32-36) moves from `date '2026-11-20'` to the next Friday after today, computed by a helper like 003's `pg_temp.ist_next_weekday` and defined in 006 itself, because past starts and starts inside the notice now read 0 free seats, and that fixed Friday stops passing at 09:30 IST on 20 November 2026. 006's other cases (row counts, first and last starts) keep their fixed dates.

**`get_availability(…)`** (M2). Same signature, grants and "zero rows, never an error" behaviour, which now also covers a cafe with app bookings switched off. `free_seats` counts only active, pledged stations, and is 0 for a start earlier than `now() + app_notice_minutes` and for a slot that overlaps a closure. Seats of counter blocks count as taken, like any unreleased seat. pgTAP 010: 0 inside the notice, 0 over a closure, unpledged stations not counted, a counter block counted.

### Sweeper (M5)

**`settle_finished_bookings() returns integer`**: definer, granted to nobody (`service_role` keeps its default). Two statements. ### Photos (M6)

**`can_write_cafe_image(p_name text) returns boolean`** (`20261117122500`, created unguarded, before the `do` block): `language sql stable security definer set search_path = public, extensions`; revoked from `public, anon, authenticated`, then granted to `authenticated`. ### Account (M7)

**`delete_my_account() returns void`** (`20261117122700`). Who: any signed-in user (`GG001`).
