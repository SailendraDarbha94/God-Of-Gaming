## 2026-11-21 — A Figma board of the player app, and what drawing it found

The founder asked for the player app's designs, screens and flow in a Figma file. The app has not run on a simulator yet (the M0 entry below), so there were no screenshots to trace: the board is drawn from the code. No spec or ADR asks for this; it is tooling and a record, and it changes nothing the apps or the database do.

- `scripts/figma-board/` (new), `README.md` (What is in the repository; Scripts) — a generator that draws `apps/player` in Figma. One builder per React Native component mirrors its nesting, tokens, strings and conditions, and imports the app's own theme, copy, formatters, slot and history logic and the fixture repositories of `@gog/data`, so nothing is retyped. `scenario.ts` drives those repositories on a fixed clock (Saturday 21 November 2026, 6:05 pm IST) to produce one player's bookings in each status. `lower.ts` resolves React Native's layout rules into explicit auto-layout sizing, and `renderer.js` draws through Figma's plugin API, which a design file's tab exposes as the global `figma`; `loader.js` is the snippet that hands it the files. The board has 65 frames (61 states of the 9 routes and 4 reference sheets) in 5 sections, 3,767 layers, 142 prototype links, 21 flow arrows, 11 colour styles and 6 text styles. Evidence: `pnpm board:build` in the repository writes a `board.json` byte-identical to the one drawn in the founder's Figma file on 21 November (same SHA-256). `loader.js` was run in a browser against a stand-in renderer: with one file it asks for both, with both it runs the renderer and reports 65 frames.
- `package.json`, `pnpm-lock.yaml` — scripts `board:build`, `board:preview` and `board:check`, and three root devDependencies: `jiti` 2.7.0, which runs the generator's TypeScript with the app's modules on the import path, and `eslint` and `@types/node` from the catalog, which `board:check` needs. All three were already in the lockfile as dependencies of other packages: the lockfile gains 9 lines, the install resolves the same 1,184 packages and downloads none. Why at the root: the folder is not a workspace package, so `pnpm check` and CI do not run it, and a change in the player app cannot fail CI through a drawing tool. `board:check` is how drift shows: it type-checks the builders against the app's real types, with `exactOptionalPropertyTypes` off as the player compiles (`packages/tsconfig/expo.json`), then lints with the shared base rules. Evidence: both pass; the first lint run reported 127 problems, 123 of them brace style fixed by `--fix`, none a non-null assertion or an unsafe type.
- `.gitignore`, `.prettierignore` — `scripts/figma-board/out/`, what `board:build` writes.
- How the drawing was checked (three workflows, 21 November). Twelve builders translated the feature components and the routes; twelve reviewers, one per file, then compared every builder with its source line by line and made 5 corrections (a wrapper frame the list does not have, a retry link, links left under a system alert, the app name and version retyped instead of read from `app.config.ts`, one caption). They also found four faults in the renderer and the chrome, fixed before the final draw: cells of a wrapped row did not share the tallest height, wrapped text in a centred column was not centred as a block, a top-aligned badge left its row 2 pt short, and the phone step drew the number pad where the code asks for the phone pad.

Two more readers took each note in turn, one to refute it against the code, one to find what the spec, the ADRs and the code comments say. The documents are silent on 59 of the 69; 10 carry what a spec, an ADR or a comment says. None is fixed here.

## 2026-11-17 — Expo patch releases no longer fail CI

CI's `expo-doctor` step compared the player app with the newest SDK 58 patches on Expo's API, so a commit that passed could fail the next day without any change: Expo published patches on 11 and 12 November (pull request 2 took them) and again on 17 November, about two hours before pull request 2 merged, which turned `main` red on its merge commit `9be5594`.

- `.github/workflows/ci.yml` (`check`, `expo-doctor`), `docs/spec/07-standards-and-verification.md` (CI job 1), `README.md` (How we work) — the step sets `EXPO_OFFLINE=1`. Why: `expo-doctor` checks dependency versions by spawning `expo install --check` with the original environment, and the CLI then validates against `expo/bundledNativeModules.json` from the installed `expo` instead of the API, so the result depends only on the lockfile. Evidence (expo-doctor 1.21.6, @expo/cli 58.1.20, 17 Nov 2026): with `expo` 58.0.25 installed, the online check failed on three newer patches and the offline check passed 20 of 20; with the local map edited to expect `expo-status-bar` ~58.0.99 and async-storage 3.1.1, the offline check failed on both, so it still catches a real mismatch such as iteration 1's async-storage pin.
- `.github/workflows/expo-sdk-patches.yml` (new) — runs `expo-doctor` against Expo's API on Mondays at 03:30 UTC and on demand, and fails when the SDK has newer patches than the lockfile. Why: without it, nothing would say when the app falls behind the SDK's bug fixes.
- Not taken here: the 17 November patches (`expo` 58.0.26, `expo-dev-client` 58.0.21, `expo-router` 58.0.32). CI no longer needs them, and the weekly check reports them, so they can be taken in a pull request a few days after release, once a bad publish would have been caught.
