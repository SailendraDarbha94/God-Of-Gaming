# 09. The partner app (`apps/partner`, `@gog/partner`)

Next.js 16 (App Router, Turbopack), React 19.3, Tailwind CSS 4, TanStack Query, TypeScript strict. Deployed later as its own Vercel project on `partner.<domain>`, functions in `bom1` (`iteration-2/07-launch.md`). ADR 0013 applies: all data access happens in the browser, the server renders static shells only, and nothing is indexed.

This is the partner app's living specification. Milestone M0 of iteration 2 created it from `iteration-2/05-partner-app.md`; it describes the app as specified for the whole iteration, says below what exists so far, and each milestone updates it with what it builds and finds. The milestones and their acceptance checks are in `iteration-2/01-scope.md`.

## Rules every screen follows

- **No data on the server.** No module that creates a client, a repository or a fixture world is evaluated during server rendering. `src/app/(app)/layout.tsx` renders a small client component that loads the signed-in shell with `next/dynamic(() => import(…), { ssr: false })`; Next 16 allows `ssr: false` only inside client components (`node_modules/next/dist/docs/01-app/02-guides/lazy-loading.md`). `src/lib/repositories.ts` starts with `import 'client-only'` and exports a function that builds everything on its first call in the browser; nothing runs at import. No Server Actions, no data Route Handlers, no `cookies()` or `headers()`, no `proxy.ts` (enforced in part by `@gog/eslint-config/partner`).
- **Phone first.** Every screen works at 360 px wide with no horizontal scroll, because the founder builds listings on a phone during visits and some counters have no PC. From 1024 px the board uses a two-column counter layout. Touch targets are at least 44 by 44 px; nothing depends on hover.
- **The role decides what is shown, the database decides what is allowed.** Screens read the caller's role from `partner_cafes` or `partner_cafe` and offer only what `iteration-2/02-roles-and-permissions.md` allows, using the `@gog/domain` helpers (`counterActions`, `publishChecklist`, `appBookingsChecklist`). A refusal from the database still gets clear copy.
- **Validate before sending.** Forms run the `@gog/domain` validators and show each `FieldIssue` next to its field; `GG011` is a backstop.
- **Copy** is plain Indian English: "Bengaluru", rupees through `formatPaise` and `formatHourlyRate`, times and dates in IST through `formatIstTime` and `formatIstDate` ("7:30 pm", "Sat, 21 Nov"). Statuses are words, not only colours. Cafe status reads Draft (not public), Listed, or Hidden; app bookings read On or Off.

## The board

The screen staff keep open all shift. It reads once per poll: `counter.listBookings(cafeId, boardRange(hours, now))`, every 30 seconds (`refetchInterval: 30_000`, `refetchIntervalInBackground: true`), when the window regains focus, and after every write.

- **Floor view** (the default). For each tier, one row per station: its label; a badge when it is pledged to the app; its state now (Free, In use until 8:30 pm with the block kind or booking code, Out of service); and its next booking today. Each row has "Walk-in": a sheet with 30 min, 1 h, 2 h and 3 h buttons that creates a `walk_in` block on that station starting now. That is two taps. "Block" opens the full form (kind, start, duration, stations or a seat count, note), and "Out of service" toggles the station (M4). The note field is labelled "For staff: no names or numbers", because a phone block's note is where staff would otherwise write who called; the database refuses phone numbers and clears block notes after 30 days (ADR 0017).
- **List view.** Today's bookings and blocks in start order, then the next seven days by day. A booking card shows the booking code in large type, the tier, the stations, start and end, the seat count, the status, and for app bookings the listed total ("₹240 at the listed rate", since the cafe collects the money); its buttons come from `counterActions` (M3 acknowledge; M4 extend, end, cancel; M5 check in, no-show, complete, move, add time).
- **New bookings.** A confirmed app booking that is not acknowledged shows in a banner at the top ("New app booking: PS5 Lounge, Sat 7:00 pm, 2 seats, code 9000A1"), with "Seen" on each and "Mark all seen". That includes bookings beyond the board's eight days, which `listBookings` returns whatever their start: the banner shows their date ("Sat 28 Nov, 7:00 pm"), and they are marked seen there, while the floor and list views keep to the range. The tab title becomes `(2) New bookings · Pixel Den`. An `aria-live="assertive"` region announces each new one.
- **Sound.** Browsers do not play audio before a user gesture: an `AudioContext` created before one starts suspended and needs `resume()` after one ([Chrome autoplay policy](https://developer.chrome.com/blog/autoplay), read 16 Nov 2026). So on every load, and whenever the `AudioContext` is not running, a persistent banner reads "Sound is off: tap to turn on" and the tab title starts with "Sound off". A remembered choice ("Sound on" pressed on this device before) never hides it; it only means the first tap anywhere turns sound on. After a reload (a PC restart, a browser update, a discarded tab) the board is silent until someone taps, and the banner says so. The alert is two short tones made with the Web Audio API (no audio file), played when a new unacknowledged booking appears and repeated every 60 seconds until none is left. "Test sound" plays it once. The banner and the title always show as well, so sound is never the only signal.
- **Changes from the player.** When a poll shows that a booking the board already had was cancelled by the player, a banner says so once, with the sound. The board works this out by comparing polls; nothing is stored.
- **Search by code.** A field filters what the board has loaded by booking code, case-insensitive, from four characters, and shows every match.
- **Needs attention** (M5). App bookings past their start plus the cafe's grace period that are not checked in, and those that ended without a check-in ("Did they come?"), with Check in and No-show buttons.
- **Moving and conflicts.** When taking a station out of service, a closure or new hours return `conflict`, the screen shows the bookings in the way, read from the board data, with Move (M5) and Cancel next to each.
- **Keeping it awake.** "Keep screen on" uses the Screen Wake Lock API where the browser has it. Browsers slow timers in hidden tabs, so on a desktop the board says to keep the tab visible; M3 measures how late a hidden tab's polls run in Chrome and records it in `docs/spec/09-partner-app.md`. On phones the board polls and sounds only while it is on screen: a frozen page runs no timers or fetch callbacks ([Page Lifecycle API](https://developer.chrome.com/docs/web-platform/page-lifecycle-api), updated 16 Oct 2026, read 16 Nov 2026), and Chrome's intent to freeze background tabs on desktop says freezing had already shipped on mobile ([blink-dev, 7 Oct 2019](https://groups.google.com/a/chromium.org/g/blink-dev/c/sotCDcI-E7Y), cited by the review of 16 Nov 2026, not reread), so a phone that is locked or showing WhatsApp gets no poll, no banner and no sound. A counter that uses a phone needs a device that keeps the board open, on charge, with "Keep screen on"; the board says so on a phone-sized screen.

## Listing, stations, settings and team

- **Details** (owner, operator): name, area (from `catalog.listAreas('bengaluru')`), address, latitude and longitude, description, amenities (the nine slugs of `AMENITY_LABELS` as checkboxes plus free tags), public WhatsApp number, map link (a Google Maps link only, the rule of `LISTING_RULES.mapsUrlPrefixes`). One Save sends the whole form (`updateDetails`). Coordinates come three ways: "Use my location", which reads the Geolocation API and shows the reading's accuracy with a map link to check it, for the founder standing at the cafe; a "Paste a Google Maps link or coordinates" field, which the app-local `coordinatesFromMapsUrl` fills from the `@lat,lng` and `q=lat,lng` forms and from a plain `12.9166, 77.6101` pair (what Google Maps copies for a dropped pin); and typing. The field's hint says that short share links (`maps.app.goo.gl/…`) hold no coordinates and cannot be read here, because `connect-src` lets the page fetch only its own origin and Supabase.
- **Hours**: seven rows, Sunday to Saturday, each closed or with opening and closing times in 30-minute steps; "overnight" is set automatically when closing is at or before opening, and shown as "(next day)"; "Copy to all days". Save sends the week (`setHours`).
- **Games**: a checklist from `catalog.listGames()`, grouped by station kind, with a filter box.
- **Stations** (owner, operator; staff see the page with only the out-of-service switch): a card per tier with kind, name, the hourly rate in rupees (converted to paise; the rule table's limits are shown), description, specs as key and value rows, and order; under it the stations with label, "Sold in the app" (the pledge), "Out of service" (M4), and Delete when the station has never been booked. "Add stations" takes labels one per line or a range ("PC-01 to PC-12"), and hints that numbering as on the floor, zero-padded, keeps the order right.
- **Settings** (M4): the app bookings switch, with `appBookingsChecklist` shown when it cannot be turned on (for an owner before approval: "The founder approves app bookings after the test booking at your counter"); for an operator, "Approve app bookings" (disabled with `approvalChecklist` until the counter test has passed) and "Withdraw approval", which also switches them off; notice period (30 minutes to 24 hours, in 30-minute steps); no-show grace period (5 to 60 minutes, applying to bookings made from then on); closures, listed with Remove, and added as "Closed all day on <date>" (the day's opening window) or a custom range with an optional note.
- **Team** (owner, operator): members with display name or "Member", the last four digits, role and joining date; pending invitations with the full number, role and expiry, with Revoke; an invite form (Indian mobile number, owner or staff). An owner sees Change role and Remove on staff rows and on their own row; another owner's row reads "Ask the founder to change or remove an owner". An operator sees both on every row. Anyone can leave a cafe from the account menu, except its last owner.

## Preview and publishing

The preview renders `previewCafe(cafe, games)` with the app's own components (ADR 0007: no UI is shared with the website): cover and gallery, name and area, address with map link, tiers with prices and station counts, grouped hours, games, amenities, and "Not taking app bookings" when the switch is off. Beside it:

- the publish checklist from `publishChecklist`, each item with a link to the screen that fixes it;
- for an owner: "I have checked this listing and I accept the partner terms" (linking to `/terms` and naming the version), and a button that records it (`acceptTerms`). After acceptance, the date and version are shown;
- for an operator: Publish when the checklist is clear; for an owner or operator: Hide, and List again (refused for an owner while the cafe is suspended);
- for an operator (M4): Suspend, which hides the cafe, switches app bookings off and lists its future bookings for the founder to keep or cancel, and Lift suspension.

The website's promise to cafes, "We set your page up and send you the link to check", is this screen. The owner sees it signed in on their own phone during the visit.

## Operator pages

- `/ops`: unacknowledged app bookings older than 10 minutes, at every cafe, polled every 30 seconds with the board's sound: cafe, start, tier, seats, booking code and age, with a link to that cafe's board. Below them, "Cancelled by the cafe" (M4, `listCafeCancellations(24)`): each cancellation of an upcoming app booking with the cafe, the reason, the start time and "Show the player's number", so the founder can ring the squad before they travel; a new one plays the board's sound. "Show the player's number" calls `bookerPhone` after a confirmation that says the lookup is recorded, and shows the number formatted for dialling. The page has the board's limits (sound off until a tap, no polling while hidden on a phone), so during the pilot it stays open on an always-on device through the opening hours of bookable cafes (open decision 5).
- `/ops/new-cafe`: name, area, address, coordinates (with "Use my location" and the maps-link helper) and slug, prefilled with `slugify` of name and area and editable. Create goes straight to the new cafe's Listing.

## Data access, sign-in and session

- `src/lib/env.ts` parses with Zod, at import, in the browser: `NEXT_PUBLIC_GOG_DATA_SOURCE` (`supabase | fixtures`, default `supabase`), `NEXT_PUBLIC_SUPABASE_URL` and `NEXT_PUBLIC_SUPABASE_ANON_KEY` (both required for `supabase`; the key is refined with `isPublishableKey` from `@gog/data/client`, ADR 0011), and the optional `NEXT_PUBLIC_WEBSITE_URL`. Each variable is read as a literal `process.env.NEXT_PUBLIC_…`, because Next inlines only literal reads into the browser bundle (`node_modules/next/dist/docs/01-app/02-guides/environment-variables.md`). `parseEnv(source)` is exported and unit-tested; `vitest.config.ts` sets the source to `fixtures`.
- `next.config.ts` checks the environment when it loads, inline, because module resolution in `next.config.ts` is limited (`node_modules/next/dist/docs/01-app/03-api-reference/05-config/02-typescript.md`). Next inlines `NEXT_PUBLIC_*` values into the static client chunks at build time, so a check that runs only in the browser would refuse a secret key after it had been served from `/_next/static`. Its rules:
  - Whenever `NEXT_PUBLIC_SUPABASE_ANON_KEY` is set, whatever the data source, it refuses a value that holds `sb_secret_` anywhere, or a JWT (`eyJ…`) whose base64url payload has a `role` other than `anon` or cannot be read, whether the JWT is the whole value or sits inside other text (a quoted or `Bearer ` paste would still be bundled), and every JWT in the value is judged, so a paste of both legacy keys cannot hide the service_role one behind the anon one: the rule of `packages/data/src/publishable-key.ts`, repeated inline. The build fails before the key is bundled.
  - Whenever `NEXT_PUBLIC_GOG_DATA_SOURCE`, `NEXT_PUBLIC_SUPABASE_URL` or `NEXT_PUBLIC_WEBSITE_URL` is set, it must be a value `env.ts` accepts, because any other value would build and then fail in every browser: the source is `supabase` or `fixtures` (not `Fixtures` or `fixture`), and each URL starts with `http://` or `https://` and parses, which is Zod's `z.url({ protocol: /^https?$/ })` (so `https:example.com` and `www.example.com` are refused). The Supabase URL's origin then goes into the CSP and the image host. Added in M0 after review.
  - Only when `VERCEL_ENV` is set: it refuses `fixtures` when `VERCEL_ENV` is `production`, and requires the URL and key when the source is `supabase`.
  - `scripts/check-build-gate.sh` (`pnpm --filter @gog/partner check:gate`, also a CI step) proves every rule case by case through `next typegen`: each refused case must fail with its own message, and the accepted ones (no variables, fixtures, a production configuration with a publishable key or an anon JWT, and http or https website URLs) must load. It has 28 cases, 21 refused and 7 accepted; removing any one rule from the gate makes at least one of them fail. Every case sets all five variables, an unset one as an empty string, because Next never overrides a variable already in the environment, so a developer's `.env.local` cannot leak into a case.

  `next typegen` loads the config in the build phase (`node_modules/next/dist/cli/next-typegen.js`), and the partner `typecheck` runs it. It, the smoke test's `next start` and CI's lint, typecheck and test step all run without `VERCEL_ENV` or a key, so the gate does not affect them; a gate that required the URL and key whenever the source is `supabase` (the default) would fail `pnpm check` on every clean clone. `env.ts` still refuses a Supabase source without URL and key in the browser. That makes the partner app's refusal of fixtures and of secret keys a pre-bundle gate, the follow-up ADR 0011 names and the player app still lacks (spec 06).

- On fixtures the shell shows a one-line note above the header, "Sample data: nothing here is real, and each browser tab has its own copy", so nobody mistakes the fixture world for a cafe's real one.
- `src/lib/repositories.ts`: on its first call, `createServerClock()`; for Supabase, `createBrowserSessionClient({ url, key, storageKey: 'gog-partner-auth', clock })`; then `createCatalogRepository`, `createAuthGateway` and `createPartnerRepositories` with the same options. On fixtures, `{ source: 'fixtures', now: clock.now }` and the shared fixture world, one per tab.
- Providers: `QueryProvider` (TanStack Query; no retries for `PartnerError`, whose codes are answers); `SessionProvider`, as the player's, subscribing to `onAuthStateChange` and removing every query when the session ends or the user changes; `CafeProvider` with the current cafe id from the route and its role.
- Query keys: `['cafes']`, `['cafe', id]`, `['board', id, from]`, `['members', id]`, `['invites', id]`, `['ops', 'unacknowledged']`, `['ops', 'cafe-cancellations']`, `['catalog', 'areas']`, `['catalog', 'games']`. Every write is a mutation that invalidates the keys it touches.
- Sign-in uses `AuthGateway` with `toIndianMobileE164`. The session lives in `localStorage` under `gog-partner-auth` and supabase-js refreshes it while the tab is open, so a counter PC stays signed in until someone signs out (`config.toml` sets no session time limit).
- Invitations: `acceptInvites()` runs whenever the signed-in shell starts with a session (after sign-in, and on every load with a stored session) and before each `listMyCafes()` on `/cafes`. An owner still signed in from branch one's visit then sees branch two after a reload, and someone who signed in before being invited is not left on the empty state.
- Rate limits: one code request per number every 60 seconds, and 30 sign-ins per five minutes per IP address by default ([Supabase rate limits](https://supabase.com/docs/guides/auth/rate-limits), read 16 Nov 2026). Staff on one cafe's Wi-Fi share the second. The copy for a rate-limit refusal says to wait a minute.
- No CAPTCHA. It is a project-wide Supabase setting that would also make the player app's sign-in send a token, and no React Native widget is documented (unverified).
- Errors: `PartnerError` codes map to copy in each feature's `copy.ts`. `forbidden`: "Your role can't do this. Ask an owner." `not_found` on a cafe: "This cafe isn't available to you", then back to `/cafes` (a removed member lands here). `conflict`: what is in the way, as above. `last_owner`: "Add another owner first." A `DataError` with code `transport`: "No connection. Nothing was saved." `DataError` is imported from `@gog/data/partner`, which re-exports it, because the lint boundary bans the `@gog/data` root.

## Security headers

`next.config.ts` sends, on every route: `X-Content-Type-Options: nosniff`, `Referrer-Policy: strict-origin-when-cross-origin`, `X-Frame-Options: DENY`, `Permissions-Policy: microphone=(), geolocation=(self)` (`self` for "Use my location"; and `camera=()` unless M6's photo input turns out to need it), `X-Robots-Tag: noindex, nofollow`, and a Content-Security-Policy: `default-src 'self'; script-src 'self' 'unsafe-inline'` (plus `'unsafe-eval'` in development only); `style-src 'self' 'unsafe-inline'`; `img-src 'self' data: blob:` plus the Supabase origin, and `https://picsum.photos` on fixtures; `connect-src 'self'` plus the Supabase origin; `font-src 'self'`; `object-src 'none'`; `base-uri 'none'`; `form-action 'self'`; `frame-ancestors 'none'`. Nonces would need dynamic rendering, which this app avoids (`node_modules/next/dist/docs/01-app/02-guides/content-security-policy.md`); Next's experimental hash-based CSP is the later way to drop `'unsafe-inline'` for scripts. The root layout's metadata also sets `robots: { index: false, follow: false }`.

## Accessibility

The target is WCAG 2.2 AA. Every control has a visible label; a control's edge (a form field, a secondary button) uses `--color-field-border` (`#6e6e88`, at least 3:1 against the page and the surfaces, SC 1.4.11), not `--color-border`, which is 1.4:1 and only separates regions; errors are listed in a summary at the top of a form and next to each field, with focus moved to the summary; colour contrast is AA; focus rings are always visible; dialogs and sheets trap focus and close with Escape; the board is fully usable with a keyboard (arrow keys move between stations, Enter opens the actions); status badges carry text; new bookings are announced through a live region; motion respects `prefers-reduced-motion`; the layout survives 200% zoom.
